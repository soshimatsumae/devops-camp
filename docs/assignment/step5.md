# Step5 進行メモ: Step4提出後の画面設計の変更点

[docs/assignment/step4.md](./step4.md)はStep4提出時点のスナップショットとして内容を固定している。このファイルには、提出後(先週以降)に議論して変更した画面設計の差分を記録する。[docs/SCREEN_LIST.md](../SCREEN_LIST.md)・[docs/SCREEN_FLOW.md](../SCREEN_FLOW.md)は生きたドキュメントのため、以下の変更はすでに反映済み。

## 1. タスク一覧の階層表示方針を「インデント表示」から「クリックで1階層ずつ展開」に変更

- **変更前**: 親子関係を階層的にインデント表示する案は、`GET /tasks`のページネーションと両立しないため見送り、`parent_id`フィルタでの絞り込み表示のみとしていた(Step4提出時点)
- **変更後**: デフォルトで親タスク(`parent_id=null`)のみを表示し、親タスク行をクリックするとその子タスクを展開、子タスク行をさらにクリックすると孫タスクを展開する、アコーディオン方式にした
- **理由**: 展開のたびに`parent_id`フィルタ付きの`GET /tasks`を呼ぶだけで実現できるため、全件取得や新しいAPIを追加する必要がなく、既存のページネーションとも両立する
- **影響**: バックエンドの変更は不要。[docs/SCREEN_LIST.md](../SCREEN_LIST.md)のS-03(下段のタスク一覧)に反映済み

## 2. タスク詳細画面(S-05)を廃止し、タスク詳細モーダル(M-03)に統合

- **変更前**: タスクの詳細確認は独立した画面(S-05)に遷移する設計だった
- **変更後**: タスク一覧の行をクリックすると、画面遷移せずにモーダル(M-03)でタスク詳細を表示する方式にした。モーダル内で子タスク行をクリックすると、同じモーダルの中身をその子タスクの詳細に差し替える(M-03→M-03の自己遷移)
- **理由**: タスクの作成・編集をモーダル方式にした理由(ページ遷移で一覧のスクロール位置やフィルタ状態を失う)と同じ理由が、詳細確認にもそのまま当てはまるため。「詳細を見るためだけに画面遷移が発生するのはおかしい」という指摘がきっかけ
- **影響**: 画面遷移図上の「S-05→S-05の自己遷移」という経路がなくなり、「M-03→M-03」に置き換わった。[docs/SCREEN_LIST.md](../SCREEN_LIST.md)・[docs/SCREEN_FLOW.md](../SCREEN_FLOW.md)に反映済み

## 3. カレンダー画面(S-03)とタスク一覧画面(S-04)を1画面のダッシュボードに統合

- **変更前**: カレンダー(S-03、ログイン後のダッシュボード)とタスク一覧(S-04)は別画面で、共通ヘッダーのナビゲーションで行き来する設計だった
- **変更後**: 両方を1画面(S-03)に統合し、上段にヒートマップを固定表示、下段にタスク一覧を配置するレイアウトにした
- **理由**: 「ヒートマップを眺める」のと「今日やるタスクを確認する」はどちらもログイン直後にまとめて見たい情報であり、画面を分けて往復させる理由がないと判断した
- **影響**: 画面遷移図からS-04ノードと、S-03↔S-04間のナビゲーション矢印が消え、全体の画面数は7→6(S-01・S-02・S-03・M-01・M-02・M-03)になった。[docs/SCREEN_LIST.md](../SCREEN_LIST.md)・[docs/SCREEN_FLOW.md](../SCREEN_FLOW.md)に反映済み

### 4-1. カレンダーのデフォルト表示期間の変更(実装済み)

Step4時点では「その年の1/1〜12/31」をデフォルト範囲とする方針にしていたが(ADR-0010)、実装を検討する過程で「1/1を起点にすると年によって1/1の曜日が異なり、GitHub風ヒートマップの曜日列(行)が年ごとにズレる」という問題に気づいた。

そのため、デフォルト範囲を「当日が属する年の1/1以降で最初に来る日曜日を起点とし、そこから53週間(371日)」に再修正した。これにより、どの年でもヒートマップの列数・曜日の並びが一定になる。ADR-0010のDecision/Consequencesを更新済み。

- 変更箇所: `internal/handlers/tasks.go`の`parseCalendarRange`
- テスト: `internal/handlers/calendar_range_test.go`の`TestParseCalendarRange_Default`を新しいデフォルト値(起点が日曜日であること、371日後がtoになること)を検証する内容に更新

### 4-2. タスク詳細(M-03)で孫タスクまで一気に展開表示(バックエンド変更不要と判明)

「1. タスク一覧の階層表示方針変更」と同じ理屈がM-03にも当てはまることに気づいた。

- **変更前の設計**: M-03内で子タスク行をクリックすると、モーダルの中身をその子タスク自身の詳細(`GET /tasks/{子のID}`)に差し替える「M-03→M-03の自己遷移」方式にしていた(Step4提出後、本ドキュメントの「2.」で決定)
- **変更後の設計**: S-03のタスク一覧と同じ「クリックで1階層ずつ展開」方式に変更し、子タスク行をクリックしたらモーダルの中身を差し替えずに、その場で`GET /tasks?parent_id=子タスクのID`を呼んで孫タスクをインライン展開する形にした。さらにクリックすれば曾孫タスクも同様に展開できる
- **理由**: 既存の`GET /tasks`の`parent_id`フィルタをそのまま使い回せるため、再帰取得APIや新しいツリー用エンドポイントを追加する必要がない
- **影響**: バックエンドの変更は不要。「M-03→M-03の自己遷移」という経路は画面遷移図から削除し(インライン展開はページ/モーダル遷移を伴わないUI内部の状態変化のため)、[docs/SCREEN_LIST.md](../SCREEN_LIST.md)・[docs/SCREEN_FLOW.md](../SCREEN_FLOW.md)に反映済み

### 4-3. タスクのキーワード検索(実装済み)

`title`/`description`を対象にした部分一致検索を、MySQLの`FULLTEXT`(`ngram`パーサー)ではなく単純な`LIKE`で実装することにした。日本語FULLTEXT検索は`ngram`パーサーの明示指定が必須で知らずに使うとヒットしないバグになりやすいこと、タスク件数も個人利用規模で`LIKE`のフルスキャンで十分なことが理由。判断の詳細は[ADR-0018](../adr/0018-task-keyword-search-like.md)を参照。

- 変更箇所: `internal/handlers/tasks.go`の`List`に`q`クエリパラメータを追加。`title LIKE ? OR description LIKE ?`の条件を`WHERE`句に加える。検索キーワード中の`LIKE`ワイルドカード文字(`%`・`_`)はエスケープしてリテラル文字として扱う
- API仕様書: [docs/API_SPEC.md](../API_SPEC.md)のTASK-01に`q`パラメータを追記
- テスト: `internal/handlers/tasks_test.go`に`TestTaskList_KeywordSearch`を追加し、titleとdescriptionそれぞれにキーワードがマッチするケースを検証

### 4-4. 「大変さ」の評価軸を5段階評価から時間ベースの工数に変更(実装済み)

Dの「並び替えの変更」に進める前に、「重さ(1〜5の5段階評価)ではなく、時間で評価したい」という要望が出て、見積もり・実績の評価軸そのものを見直した。

- **変更前**: `estimated_weight`/`actual_weight`(`SMALLINT`、1〜5の5段階評価)
- **変更後**: `estimated_hours`/`actual_hours`(`DECIMAL(6,1)`、時間単位の小数、0.5時間刻み、0.5〜9999の範囲)。列名も実態に合わせて改名した
- **理由**: 「見積もりが1→3にズレた」より「2時間の見積もりが5時間かかった」の方が差分の大きさを具体的に把握できる。判断の詳細は[ADR-0019](../adr/0019-weight-to-hours.md)、既存のADR-0008(値の分離自体の決定)との関係も同ADRに記載
- **影響範囲**: `schema.sql`(列の型・列名変更)、`internal/models/models.go`(`EstimatedHours`/`ActualHours`を`float64`で表現)、`internal/handlers/tasks.go`(Create/Update/Get/List/Calendarの全エンドポイント、新規の値域バリデーション`validHours`、エラーコード`ESTIMATED_HOURS_REQUIRED`/`ACTUAL_HOURS_REQUIRED`)、`internal/handlers/tasks_test.go`(フィールド名変更+値域バリデーションのテスト追加)、`docs/API_SPEC.md`・`docs/DB_SPEC.md`・`docs/ER_DIAGRAM.md`・`docs/SCREEN_LIST.md`・`docs/code-walkthrough/`配下の関連ファイル、`README.md`のcurl例
- **注意**: 既存のローカルDBを使っている場合、`schema.sql`を再適用(テーブル再作成)するか、手動で`ALTER TABLE`する必要がある。マイグレーションの仕組みは未導入のため、現時点では手動での追従が前提

### 4-5. 並び替えの変更(実装済み)

`GET /tasks`(TASK-01)に`sort`クエリパラメータを追加し、「締切日順」(`due_date_asc`/`due_date_desc`)と「見積もり工数順」(`estimated_hours_asc`/`estimated_hours_desc`)の並び替えに対応した。「実績工数順」は未完了タスクの`actual_hours`が`NULL`になるため実用性が低いと判断し対象外にした。

`ORDER BY`句はSQLのプレースホルダで値として束縛できない(カラム名・方向はSQL構文の一部)ため、ユーザー入力をそのまま連結するとSQLインジェクションの通り道になる。そのため`validSorts`というホワイトリスト(`map[string]string`)を用意し、この4つの値だけを信頼できる`ORDER BY`句にマッピングする方式にした。判断の詳細は[ADR-0020](../adr/0020-task-list-sort-whitelist.md)を参照。

- 変更箇所: `internal/handlers/tasks.go`の`List`に`sort`クエリパラメータを追加。`validSorts`になければ`400 INVALID_SORT`
- API仕様書: [docs/API_SPEC.md](../API_SPEC.md)のTASK-01に`sort`パラメータを追記
- テスト: `internal/handlers/tasks_test.go`に`TestTaskList_SortByEstimatedHours`(昇順ソートの確認)・`TestTaskList_InvalidSort`(ホワイトリスト外の値は400)を追加

### 4-6. 一括操作(複数選択しての削除・完了)はスキップ

実装方針を検討する過程で、一括完了の仕様を詰めるのが難しいことが分かった。タスクごとに実績工数(`actual_hours`)は本来異なる値になるはずで、「選択した複数タスクに同じ`actual_hours`を一括入力する」のは実態とずれるし、かといって「タスクごとに`actual_hours`を個別入力できる一括完了UI」を作るなら、結局1件ずつ編集モーダル(M-02)を開くのとあまり変わらない。

この過程で「複数選択して一括操作する」という機能自体の必要性が薄いと判断し、今回はスキップすることにした(一括削除だけなら単純に実装できたが、片方だけ対応するのも中途半端なため)。バックエンドの変更は行わない。

### 4-7. タスクを「リスト」でグルーピングする機能(実装済み)

Step4では「新しいテーブル(`lists`)の追加、`tasks`への`list_id`カラム追加、`GET /lists`のようなAPI新設、`GET /tasks`への`list_id`フィルタ追加など、バックエンド側の変更が必須」として見送っていたものを実装した。判断の詳細は[ADR-0021](../adr/0021-task-list-grouping.md)を参照。

- **`lists`テーブルを新設**(`id`/`user_id`/`name`/`created_at`/`updated_at`)。`tasks`に`list_id`(NULL許容、`lists.id`へのFK、`ON DELETE SET NULL`)を追加した
- **`list_id`を設定できるのは親タスク(`parent_id`が`NULL`)のみ**とした。子・孫タスクは自分自身の`list_id`を持たず親タスクの所属リストに従う、という整理にすることで「子タスクだけ別のリストに属する」という混乱を防いだ。`parent_id`と`list_id`を同時指定すると`422 LIST_ID_NOT_ALLOWED_FOR_CHILD_TASK`で拒否する
- **リストを削除してもタスクは消えない**。`ON DELETE SET NULL`により、所属タスクの`list_id`が`NULL`に戻るだけにした。リストはタスクを分類するための緩いラベルという位置づけのため
- 新しいエンドポイント`LIST-01`〜`LIST-04`(`GET/POST /lists`、`PATCH/DELETE /lists/{id}`)を追加。`GET /tasks`には`parent_id`と同じ要領(整数指定または`"null"`指定)で`list_id`フィルタを追加した
- 変更箇所: `schema.sql`(テーブル追加・カラム追加)、`internal/models/models.go`(`List`構造体、`Task.ListID`)、`internal/handlers/lists.go`(新規、`ListHandler`のCRUD)、`internal/handlers/tasks.go`(`List`/`Create`/`Update`に`list_id`対応を追加)、`main.go`(`/lists`系ルーティング追加)
- テスト: `internal/handlers/lists_test.go`を新規作成。リストのCRUD一連の流れ、リスト削除時にタスクの`list_id`が`NULL`に戻ること、子タスクへの`list_id`指定が拒否されること、存在しない`list_id`が拒否されることを検証
- ドキュメント: `docs/DB_SPEC.md`・`docs/API_SPEC.md`・`docs/ER_DIAGRAM.md`・`docs/code-walkthrough/`配下を更新
- **注意**: `lists`テーブルの追加を伴うため、既存のローカルDBを使っている場合は`schema.sql`を再適用(テーブル再作成)する必要がある
- **未着手**: フロントエンドの画面設計(S-03下段のタスク一覧をリストごとに区切って表示する、M-01/M-02でリストを選択する等)はまだ行っていない。Step6以降で改めて設計する

これで、Googleカレンダー連携を除く「次回までに修正したいこと」はすべて対応が完了した(一括操作はスキップという結論に到達)。

## 6. 画面遷移図を「画面間の関係図」から「ユースケース別フロー図」中心の構成に変更

Step4提出時のSCREEN_FLOW.mdは、全画面・全モーダルの遷移を1本のmermaid図にまとめていた。これは「どの画面からどのモーダルを開けるか」を俯瞰するには向いているが、以下の問題があった。

- 開始・終了地点が明示されず、1つのユースケースの中でどこからどこまでが一連の流れなのか読み取りにくい
- 正常系・准正常系・異常系(バリデーションエラー、401など)の分岐が1本の図に混在し、特に異常系の経路が追いにくい

そのため、以下の2段構成に変更した。

- **画面の関係性(静的マップ)**: 元の1本の図を簡略化して残す。「どの画面からどのモーダルを開けるか」の一覧性を保つのが目的で、エラー分岐などは含めない
- **ユースケース別フロー図**: 主要な6つのユースケース(ログイン、新規登録、タスク作成、タスク完了、タスク削除、セッション切れ・未ログインアクセス)それぞれについて、開始・終了ノードと正常系/異常系の分岐を明示したmermaidのフローチャートを個別に作成した。エラーメッセージは実際にワイヤーフレームへ入れた文言をそのまま使い、画面名にはワイヤーフレームのタブ名を併記することで、フロー図とモックアップが相互に参照し合える状態にした

旧版にあった「遷移トリガーの一覧」表は、各ユースケースのフロー図がより詳細な情報(エラーコード・エラーメッセージ込み)を提供するため廃止した。

さらに、ワイヤーフレームの各画面を縮小して並べ、ボタンなどの操作の起点から次の画面へ、ユースケースごとに色分けした矢印でつないだ[画面フローマップ](../design/README.md#画面フローマップ)を作成した。mermaidのフロー図は分岐の論理を、フローマップは「どの画面のどのボタンから遷移するか」を見せる役割で使い分ける。

ワイヤーフレームとフローマップは当初Claudeのartifactとして作っていたが、artifactは同じチームの人しか見られないため、元データのHTMLを[docs/design/](../design/README.md)でリポジトリ管理し、GitHub上ではHTMLから書き出したPNGを表示する形にした。PNGは`./scripts/export-design-images.sh`(Chromeのヘッドレスモードを使用)で書き出す。
