# Step4 課題提出: フロントエンド1

## 概要

- バックエンドAPI([docs/API_SPEC.md](../API_SPEC.md))に対応する画面を洗い出し、画面一覧・画面遷移図としてまとめた。
- SPA(Single Page Application)構成を想定している。ページ全体のリロードを伴う画面遷移(サーバーサイドレンダリング的な遷移)ではなく、クライアント側のルーティングでS-01〜S-05を切り替え、タスクの作成・編集はモーダルで画面上に重ねて表示する。
- タスクの作成・編集はモーダル方式、ログイン後のダッシュボード画面はカレンダー(ヒートマップ)画面とする方針で設計した。

## 画面遷移図

## 設計判断の背景

- **モーダル方式の採用**: タスクの作成・編集をページ遷移にすると画面数が増え、一覧のスクロール位置やフィルタ状態を失う。モーダルにすることでSPAらしい操作感を保った。
- **カレンダーをダッシュボードにする**: 想定ユーザーである私がログインして最初に見たい（嬉しいから）、というだけの理由による。

## 想定するユーザー動線（例）

1. ログイン → カレンダー(S-03、ダッシュボード)で直近の頑張りを確認 → 共通ヘッダーからタスク一覧(S-04)へ移動 → 今日着手するタスクを確認/作成(M-01)
2. タスク一覧(S-04)から作業対象のタスクをクリック → 詳細画面(S-05)で内容確認 → 編集モーダル(M-02)で`status`を`in_progress`に変更
3. タスク詳細画面(S-05)→ 編集モーダル(M-02)で`status`を`done`に変更し、`actual_weight`を入力 → モーダルを閉じると詳細画面に`completed_at`が反映される → カレンダー(S-03)に戻ってその日の合計に反映されていることを確認
4. タスク作成時(M-01)に「これは見積もりが大きすぎる」と感じたら、作成後に詳細画面(S-05)から「子タスクを追加」ボタンで分割する
5. 初回のみ、新規登録画面(S-02)→ 登録成功後にログイン画面(S-01)へ戻り、改めてログインする

## カバーしていない操作パターン・未設計のもの（やりたいです）

- **Googleカレンダー連携**: 可能であればとしていたが、API仕様書にも対応するエンドポイントがなく、画面も設計していない。


### バックエンドAPIの制約上、現状では対応する画面を作れないもの

- タスクのキーワード検索
- 並び替えの変更
- 一括操作(複数選択しての削除・完了)
- タスクを「リスト」でグルーピングする機能

これらに追加対応する場合は、Step6(実装)より前に、DB仕様書・API仕様書の改訂とADRの追加をセットで行う(「次回までに修正したいこと」にも記載)

## 設計中に苦労したこと・判断に迷ったこと・学んだこと

### 1. タスク詳細画面で孫タスクまで取得できない問題

`GET /tasks/{id}`(TASK-03)の実装(`internal/handlers/tasks.go`の`Get`)を読み返すと、`parent_id = 対象ID`の直接の子タスクのみを1階層分取得しており、孫タスクまでは含まれていないことに気づいた。ER図([docs/ER_DIAGRAM.md](../ER_DIAGRAM.md))でもAPIレスポンス自体は再帰的にツリーを返す設計になっていない。

これにより、画面設計でも「タスク詳細画面(S-05)で孫タスクまで一気に展開表示する」という案は採れないと判断した。孫タスクを見るには、子タスクの行をクリックしてその子タスク自身の詳細画面(S-05)へ再度遷移する(S-05→S-05の自己遷移)という形にせざるを得ない。これはバックエンドの実装を読み返してAPIの挙動を実際に確認しないと気づけなかった制約だったと感じている。

直したいので、「次回までに修正したいこと」にも記載

### 2. タスク一覧はAPIの都合上「完全な木構造」では表示できない

`GET /tasks`(TASK-01)は`user_id`条件のみのフラットな一覧に`LIMIT`/`OFFSET`でページングをかけている。親タスクと子タスクが区別なく同じページネーションの対象になるため、「1ページ目に子タスクだけが表示され、その親タスクは2ページ目にいる」という状態が普通に起こりうる。

そのため現状の設計では、一覧画面では暫定的に`parent_id`フィルタ(親タスクのみ表示、または特定の親の子のみ表示)を使って絞り込む形にしているが、こちらも直したいので、「次回までに修正したいこと」にも記載

### 3. 「ログアウト」と「セッション切れ」を同じ矢印で表現していいのか迷った

画面遷移図では、共通ヘッダーの「ログアウトボタン」と「未ログイン状態でのアクセス(トークン期限切れ含む)」を、どちらも同じ「S-01へ戻る」という矢印で表現した。実装上はどちらも「トークンを持たない状態でS-01に遷移する」という点で同じだが、ユーザー体験としては以下のように意味が違う。

- **能動的なログアウト**: 自分の意思で終了した。何も案内は不要
- **セッション切れ**(JWTの有効期限は1時間、[ADR-0004](../adr/0004-jwt-auth.md)): 操作中に突然ログイン画面へ戻され、理由が分からず戸惑う可能性が高い

後者には「セッションの有効期限が切れました。再度ログインしてください」のような気がしているが、これはバックエンドが「トークンが無効/期限切れ」の場合も「トークンが未指定」の場合も同じ`401 UNAUTHORIZED`を返す設計になっているため、フロントエンドは`401`が「未ログイン」なのか「期限切れ」なのかをレスポンスだけからは区別できないことに気づいた。

実際に使うのは松前個人がメインになるはずなので、このままでもいいっちゃいいのだが、一般的なベストプラクティスをお伺いしたい。

## 次回までに修正したいこと

- **カレンダーのデフォルト表示期間を変更する**: ダッシュボード(S-03)を開いた際のデフォルト表示期間を「ログイン時点の年の1/1〜12/31」にする。`GET /tasks/calendar`(TASK-06)のデフォルト範囲(現状は「当日から365日前〜当日」、[ADR-0010](../adr/0010-calendar-date-range-params.md))自体を変更する必要があるため、バックエンドの修正が必要
- **期限超過タスクの強調表示・通知**: `GET /tasks`のレスポンスに含まれる`due_date`とクライアント側の現在時刻を比較すれば判定できるため、基本的にはフロントエンド側の表示ロジックのみで対応可能。ただし「通知」(ログインしていない時にも知らせる)まで踏み込むなら、バッチ処理やメール送信などバックエンド側の新機能が必要になる
- **Googleカレンダー連携**: OAuth連携・Google Calendar APIとの認証情報のやり取り・タスクとGoogleカレンダーの予定を紐付けるカラムの追加など、バックエンド側に新機能一式の追加が必要（優先度低め）
- **タスクを「リスト」でグルーピングする機能**: 新しいテーブル(例: `lists`)の追加、`tasks`への`list_id`カラム追加、`GET /lists`のようなAPI新設、`GET /tasks`への`list_id`フィルタ追加など、DB設計・API仕様書の変更を伴う(詳細は上記「カバーしていない操作パターン」参照)
- **見積もりと実績の差分を振り返るためのUI**: `estimated_weight`/`actual_weight`は既存カラムでAPIも返しているため、フロントエンドの表示ロジックのみで対応可能。ただし「差分の推移をグラフで見る」のような集計を伴う場合は、集計済みデータを返す新しいAPI(例: `GET /tasks/estimate-accuracy`)の追加を検討する必要がある
- **一覧画面(S-04)で親子関係を階層的にインデント表示したい**: 「苦労したこと2.」で見送った案。`GET /tasks`(TASK-01)は`LIMIT`/`OFFSET`によるフラットなページネーションのため、親子関係をインデント表示するには全件取得してクライアント側でツリーを組み立て直す必要がある。実現するには、ページネーションを外した全件取得モード(例: `tree=true`クエリパラメータ)を別途用意するか、階層表示自体をあきらめて`parent_id`フィルタでの絞り込み表示のままにするかを判断する必要がある。API仕様書([docs/API_SPEC.md](../API_SPEC.md))の改訂とADRの追加(なぜ全件取得モードを追加するか)を伴うため、Step6(実装)より前に設計から見直す
- **タスク詳細画面(S-05)で孫タスクまで一気に展開表示したい**: 「苦労したこと1.」で見送った案。`GET /tasks/{id}`(TASK-03)は`parent_id = 対象ID`の直接の子タスクのみを1階層分取得する実装のため、孫タスク以下を含めるには再帰的に子孫まで辿るように変更する(または`GET /tasks/{id}/tree`のような別エンドポイントを新設する)必要がある。現状は子タスクそれぞれに対してさらに子を辿るクエリ(再帰CTEや複数回クエリでの組み立て)が必要になる。こちらもAPI仕様書の改訂とADRの追加を伴うため、Step6(実装)より前に設計から見直す
- **タスクのキーワード検索**: `GET /tasks`(TASK-01)に`q`のようなキーワード検索クエリパラメータを追加し、`title`/`description`を対象にした`LIKE`検索(または全文検索)をSQLに組み込む必要がある。API仕様書の改訂を伴う
- **並び替えの変更**: `List`ハンドラの`ORDER BY created_at DESC`固定を、`sort`のようなクエリパラメータで「重さ順」「締切日順」などに切り替えられるようにする必要がある。API仕様書の改訂を伴う
- **一括操作(複数選択しての削除・完了)**: 複数IDをまとめて指定できるAPI(例: `DELETE /tasks`に`ids`配列を受け取る、または`PATCH /tasks/bulk`のような新設エンドポイント)が必要。単体操作用のAPIとは別に、権限チェック(自分のタスクのみ対象にする等)を複数件分まとめて行うロジックの追加も伴う

## まとめ

Step4を通して一番学んだのは、画面設計はフロントエンド単体では決められず、バックエンドの実装の細部(ページネーションの有無、エラーレスポンスの粒度、階層データの返し方)を読み返すたびに前提が覆る、ということだった。当然と言えば当然だが、フロントエンドとバックエンドを反復横跳びしている感じになっており、個人だから良いものの大人数で開発するような大規模なアプリケーションなら、このコミュニケーションは大変なんだろうなと感じた。

フロントエンドの設計をしながら、バックエンドの修正の必要性に気付いたものの、現状のバックエンド設計をフロントに落とし込むならこういう形だろうなという暫定的なものに仕上げた。今後はバックエンド修正→それに応じてフロントも修正のような進め方になると認識している。
