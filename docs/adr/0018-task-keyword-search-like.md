# 0018: タスクのキーワード検索は`LIKE`による部分一致で実装する

## Status

Accepted

## Context

Step4の画面設計時に、「タスクのキーワード検索」は`GET /tasks`(TASK-01)に対応するクエリパラメータがないため画面設計を見送っていた([docs/assignment/step4.md](../assignment/step4.md))。Step5でこれを実装するにあたり、`title`/`description`を対象にした検索方法として、単純な`LIKE '%keyword%'`による部分一致検索と、MySQLの`FULLTEXT`インデックス(`MATCH() AGAINST()`)による全文検索を比較検討した。

`FULLTEXT`は関連度順の並び替えやBoolean Mode(`+A +B`のような複数キーワードのAND/OR指定)に標準対応する一方、以下のデメリットがある。

- MySQLのデフォルトのFULLTEXTパーサーは単語の区切りに空白を前提にしており、単語間にスペースがない日本語ではうまく機能しない。日本語で機能させるには索引作成時に`WITH PARSER ngram`を明示的に指定する必要があり、知らずに運用すると「検索してもヒットしない」バグになりやすい
- `NATURAL LANGUAGE MODE`は「全体の50%以上の行に出現する単語は無視する」という仕様があり、タスク件数が少ないうちは直感に反した除外が起きやすい
- スキーマ変更(マイグレーション、FULLTEXT INDEXの追加)が必須で、実装・テストのコストが`LIKE`より高い

このアプリは個人利用が前提で、タスク件数も大規模にはならない想定のため、`FULLTEXT`の強み(大量データでの検索速度、関連度順ソート)の恩恵は薄い。

## Decision

`GET /tasks`(TASK-01)に`q`クエリパラメータを追加し、`title LIKE '%q%' OR description LIKE '%q%'`による部分一致検索を実装する(`internal/handlers/tasks.go`の`List`)。`q`に含まれる`LIKE`のワイルドカード文字(`%`・`_`)はエスケープし、検索キーワードとして文字通り扱う。

## Consequences

- スキーマ変更・マイグレーションが不要で、既存の`WHERE`句に条件を1つ追加するだけで実装できる
- 複数キーワードでのAND検索や、関連度順の並び替えは今回のスコープに含めない。将来的にタスク件数が大幅に増えて`LIKE`のフルスキャンが性能上の問題になった場合、改めて`FULLTEXT`(`ngram`パーサー指定)への移行を検討する
- `LIKE`はインデックスを活用できない(先頭に`%`がある部分一致のため)。現状のタスク件数の規模では問題にならないが、将来の性能劣化要因として認識しておく
