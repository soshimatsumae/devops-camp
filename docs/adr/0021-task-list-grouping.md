# 0021: タスクを「リスト」でグルーピングする機能を追加する

## Status

Accepted

## Context

Step4の画面設計時に、「Googleのタスクのように、タスクを自分で作った『リスト』(例: プロジェクトA/プロジェクトB)に分類したい」というアイデアが出たが、バックエンドの変更が必須なため見送っていた([docs/assignment/step4.md](../assignment/step4.md))。

`tasks.parent_id`の自己参照(子・孫タスク)は既存の「タスク同士の親子関係」であり、「リスト」(タスクを横断的にグルーピングする入れ物)とは別の概念。既存のテーブル構造を流用せず、新しい概念として設計する必要がある。

## Decision

新しい`lists`テーブル(`id`/`user_id`/`name`/`created_at`/`updated_at`)を追加し、`tasks`に`list_id`(NULL許容、`lists.id`への外部キー)を追加する。

- **`list_id`は親タスク(`parent_id`が`NULL`のタスク)にのみ設定できる**。子・孫タスクは自分自身の`list_id`を持たず、親タスクの所属リストに従うものとして扱う。これにより「子タスクだけ別のリストに属する」という混乱を防ぐ。作成時(`POST /tasks`)・更新時(`PATCH /tasks/{id}`)とも、`parent_id`(既存タスクの場合は既存の`parent_id`)が設定されている状態で`list_id`を指定すると`422 LIST_ID_NOT_ALLOWED_FOR_CHILD_TASK`で拒否する
- **リストを削除しても、所属していたタスクは削除されない**。`ON DELETE SET NULL`により`list_id`が`NULL`に戻るだけで、タスク自体は「どのリストにも属さない」状態で残る。リストはタスクを分類するための緩いラベルであり、ラベルを消したらタスク本体まで消えるのは直感に反するため
- `lists`のCRUD用に`LIST-01`〜`LIST-04`(`GET/POST /lists`、`PATCH/DELETE /lists/{id}`)を新設する。`GET /tasks`には`list_id`フィルタ(`parent_id`フィルタと同じ要領で、整数指定または`"null"`指定)を追加する
- リストの所有者チェック・ページネーションの要否などは、既存の`tasks`の設計パターン(`WHERE user_id = ?`で所有者チェックを兼ねる、他ユーザーのリソースは`404`)をそのまま踏襲する。リスト件数は個人利用で大きくならない想定のため、`GET /lists`はページネーションなしで全件返す

## Consequences

- タスクとリストが1(あるいは0)対多の緩い関係になり、タスクの作成・編集フローに「リストを選択する」という1ステップが増える。フロントエンド側のM-01(作成モーダル)・M-02(編集モーダル)・S-03(ダッシュボード、下段のタスク一覧)の画面設計の見直しが必要(Step4では未設計、今後のフロントエンド実装時に反映する)
- `lists`テーブルの追加に伴い、`schema.sql`・`docs/DB_SPEC.md`・`docs/ER_DIAGRAM.md`・`docs/API_SPEC.md`の更新が必要になった(本ADRとセットで反映済み)
- 子タスクが親と異なるリストに「見た目上」属しているように見えることはない(子タスク自体がlist_idを持たないため)が、将来「子タスクだけ別のリストに移したい」という要望が出た場合は、この制約を緩めるかどうかを改めて設計判断する必要がある
